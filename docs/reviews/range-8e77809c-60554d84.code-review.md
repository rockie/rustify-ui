## 1 评审对象与意图

九包 crates.io 发行从「一个库修订 R 覆盖全部包」改为「每个包记录自己的 `source_rev`」：新增归档复用（`package-libraries --reuse`）、打包决策命令（`plan-libraries`）、以及配套的 freeze/package/validate/verify/publish 调整与文档。意图是让只改 CLI（或只改某个叶子库）时不再连坐重发其余包。

## 2 确认问题

### F-01 · [P3] 新增包无法复用旧发行目录，只能回退全量打包

- 定位：`scripts/crates-io.py:598-600`（`library_packaging_plan`）
- 问题：`plan-libraries`/`package-libraries --reuse` 对上一版 receipt 里不存在的包直接报 `previous receipt has no <name> archive to reuse`。将来向 `release/crates-io.toml` 增加第十个包时，正确动作应是「新建归档并给新版本」，现在却只能绕过 `--reuse` 全量打包，且错误信息把这个正常场景描述成复用失败。
- 证据：`library_packaging_plan` 只处理 `prior is not None` 的分支；`reuse_archives`（`scripts/crates-io.py:618-634`）也只遍历 `action == "reuse"` 的条目。全量路径（不传 `--reuse`）仍然可用，因此不阻塞现有发行。
- 修复与验证：`prior is None` 时产出 `{"action": "package", "previous_version": None}`，并跳过版本比较；补一条「上一版没有该包时计划为 package」的单元测试。
- 置信度：高（代码路径唯一）。

### F-02 · [P3] 锁闭包按名字展开，同名多版本会过度合并

- 定位：`scripts/crates-io.py:565`（`locked_closure`）
- 问题：`dependencies` 里的 `"syn 2.0.119"` 与 `"syn"` 都被 `split(" ")[0]` 折成名字，随后把该名字的**所有**版本并入闭包。若某个库只用 `syn 2`，而工作区锁里还有另一条链引入 `syn 1`，升级 `syn 1` 也会把该库判为「已变更」，要求升版重打。方向保守（不会漏判、不会产出错误归档），代价是不必要的版本号与上传。
- 证据：`locked_closure` 的 `by_name` 收集同名全部条目；测试 `test_a_third_party_bump_under_a_library_closure_marks_it_changed` 只覆盖了单版本场景。
- 修复与验证：`dependencies` 项带版本时按 `(name, version)` 精确入队，不带版本时才退回按名字全量；补一条「同名两版本、只有库里用到的那个升版」的用例，断言不触发重打。
- 置信度：高（当前工作区锁确有 `syn` 1.0.109 / 2.0.119 / 3.0.5 三份）。

## 3 已核对、未构成缺陷

- **框架三包同步移动**（`scripts/crates-io.py:610-614`）：CLI 的 `framework-release.json` 只承载一个 `library_rev`，`framework_revision()` 也拒绝跨修订的三包。工具在打包前给出「也要升 X」的明确错误，属有意约束，已写入 `AGENTS.md` 与发行文档。
- **workspace 版本限制**：八个库仍共享 `[workspace.package] version`，所以今天任何库升版都会改八个 manifest，`plan-libraries` 会如实报八个 `package`；按包隔离要先把某个包的 `version` 写死。文档（`docs/crates-io-release.md`「give a package its own version」）与 `AGENTS.md` 都已说明，不作为缺陷。
- **根 `Cargo.toml`/`mise.toml`/`release/crates-io.toml` 仍算所有包的输入**：工具链或工作区依赖变化会触发全量重打，方向保守且与原行为一致。
- **`plan-libraries --rev` 要求完整 SHA**：与既有 `checkout()` 一致，`AGENTS.md` 已写明。
- **`library_rev` 语义**：现在只表示框架三包的修订，`verify`/`package_cli` 的比对都改用 `framework_revision()` 计算，receipt 内的取值同源。
