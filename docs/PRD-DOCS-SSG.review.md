### [P1] F-01 · 早期出口提前要求 P4 搜索及后期完整能力

- **定位**：[PRD](PRD-DOCS-SSG.md):306（F6/AC-2，P2）、333（F7/AC-5，P1）、651（N3/AC-4，P1）、840–843（期次出口）；对照 369、383–386（F9 全部 P4）、394（F10 P3）。
- **场景与问题**：维护者交付 P1 静态内容站时，404 必须能打开搜索，手机必须完成搜索，桌面必须通过“全部读者端验收”；P2 定制页又必须能被站内搜索找到。按这些出口，需要提前交付 P4 搜索，或将尚未达到的出口记作通过。“全部读者端验收”还隐含提前要求演示与语言切换。
- **证据**：上述 AC 已被 §7.1 的 P1/P2 出口引用；§7.2 将 F9 全部留在 P4。编号分配虽一致，AC 语义与交付顺序冲突。
- **最小修订**：保留 P4 搜索安排，将 F6 的搜索可发现性、F7 的搜索恢复入口分配到 P4；P1 404 保留返回首页等当期可用入口。浏览器矩阵从 P1 起检查当期已交付能力，并在各期复核新增能力。同步需求正文、AC、UAT 与 §7.1–7.3，不删除终局承诺。
- **复核条件**：P1/P2 可在不使用后期能力的条件下完成出口；P4 仍覆盖定制页搜索、404 搜索入口及完整浏览器矩阵。
- **置信度**：高，直接文内冲突。**阻塞**：P1/P2 计划与阶段验收交接。

### [P1] F-02 · “任意静态托管”缺少自定义 404 与策略交付的成立条件

- **定位**：[PRD](PRD-DOCS-SSG.md):9、141（S7）、333（F7/AC-5）、494–497（F14）、648（N3/AC-1）、781（Q4）、823（UAT-7）。
- **场景与问题**：维护者把目录型页面原样上传后，访问不存在的地址必须显示框架生成的 404，而且按当前语言显示。生成一个静态 404 文件本身不能决定托管服务如何响应任意不存在的路径；没有服务器重写不等于自动具备自定义错误页。严格 CSP 如何在线上交付也依赖托管能力。Q4 将部署位置描述为不影响验收，掩盖了这些必要条件。
- **证据**：[GitHub Pages 官方自定义 404 文档](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-custom-404-page-for-your-github-pages-site)要求发布 `404.html` 或 `404.md`；这属于宿主识别的约定，不能由任意文件服务推导。现有 [serve.rs](../xtask/src/serve.rs):135–138 只做目录索引，324–338 对不存在路径默认返回文本 404，说明目录索引与定制 404 是不同能力。此处不把现有预览缺少新能力当作缺陷，而是核实产品承诺所依赖的行为。
- **最小修订**：定义静态托管的最低条件：目录索引、自定义 404 的接入约定、所需 CSP 的交付能力；“不需要 SPA 重写”可保留。明确只有一个宿主错误页时如何确定语言，以及无脚本时的默认语言。部署说明与 `preview` 应体现相同契约。Q4 在完成这些条件核对前不能宣称部署位置与验收无关。
- **复核条件**：根路径、子路径与未知深路径都有明确预期；支持范围与必要宿主配置清楚；未知地址的恢复入口和语言不依赖未说明的宿主能力。未来实际部署验收仍须从目标托管环境验证。
- **置信度**：高，公开产品承诺缺少必要宿主契约。**阻塞**：G4、S7/UAT-7 与 P1 部署交接。

### [P2] F-03 · 水合前置误写成 `mount` 拒绝已有内容

- **定位**：[PRD](PRD-DOCS-SSG.md):38（E3）、750（DEP-3）。
- **场景与问题**：开发计划据此识别预渲染接管的增量时，可能把问题理解为放宽容器检查；实际需要的是接管既有静态 DOM 的入口。
- **证据**：[mount.rs](../crates/rustify-ui/src/mount.rs):89–97 检查 `MOUNTED_ATTRIBUTE`，拒绝已有作用域占用，而不检查容器是否已有内容；131–149 新建根并调用 `mount_to`；161–172 使用 `append_child`。现有路径是追加根后 CSR 挂载，没有水合接管。
- **最小修订**：将 E3 与 DEP-3 改为“现有 mount 创建新根并 CSR 挂载，尚无接管既有静态 HTML 的入口；占用检查针对已挂载作用域”。保留水合作为本次真实增量。
- **复核条件**：两处现状与源码一致，DEP-3 不被缩减成容器检查调整。
- **置信度**：高，行为级源码核实。**阻塞**：DEP-3 的下游设计交接。

### [P2] F-04 · 声称沿用仓库 CSP，实际列出的策略不同

- **定位**：[PRD](PRD-DOCS-SSG.md):46（E11）、497、505（F14 预览）、640（N3 策略）、737（沿用仓库契约）。
- **场景与问题**：维护者按 PRD 配置预览，而按仓库原契约部署，两者使用的策略不同。N3 的完整字面值缺少 `media-src 'self'`、`form-action 'none'`、`frame-ancestors 'none'`；媒体、表单和外部嵌入的边界改变。CSP 违规为零并不能证明使用的是同一条策略。
- **证据**：[compatibility.md](compatibility.md):34–35 与 [serve.rs](../xtask/src/serve.rs):36–39 含上述三项。尤其 `frame-ancestors` 不继承 `default-src`，且不能通过 meta 生效，见 [CSP3 编辑草案 §6.4.2](https://w3c.github.io/webappsec-csp/#directive-frame-ancestors)；不能把缺项视作等价省略。
- **最小修订**：统一 E11、N3、预览和部署说明采用的完整策略；若本产品有意调整策略，明确差异及理由。策略的选择与托管交付条件一起核对，但不要通过默默删指令让 Q4 看似成立。
- **复核条件**：原文中所有“沿用严格 CSP”的引用指向同一明确契约；预览与线上验收分别确认策略生效和零违规。
- **置信度**：高，原文与源码直接差异；未实测，不宣称已发生漏洞。**阻塞**：N3/F14 的策略验收交接。

### [P2] F-05 · AI 输出的公开地址及缺配置状态尚未闭合

- **定位**：[PRD](PRD-DOCS-SSG.md):423、433（无站点地址可构建）、445–451、455–458（F12）、494、503（目录型页面及子路径）、781、824（UAT-8）。
- **场景与问题**：外部工具读取 `/rustify-ui/` 下的站点时，`/llms.txt` 未说明是域名根还是部署基路径；目录型首页和内容页直接“在页面地址后加 .md”没有唯一公开映射。缺少站点地址时构建必须成功，但 F12 同时要求绝对链接且写“依赖：无”，没有规定 AI 输出和复制入口的状态。
- **证据**：以上公开契约组合造成歧义。[llms.txt 现行提案](https://llmstxt.org/)（修改日期 2026-08-10，Proposal/Format）允许文件位于子路径，并为无文件名的页面给出 `index.md` / `index.html.md` 的参照。该提案不是本项目强制标准，但说明子路径无需把文件放到域名根。
- **最小修订**：给出根部署、子路径部署、首页、目录型内容页和语言版本的 AI 文件地址实例；选择缺站点地址时的行为，例如可解析的相对链接，或启用 AI 输出时要求地址，或明确省略并警告。统一 F11、F12、复制入口与 UAT-8 的口径。
- **复核条件**：外部工具从部署基路径的索引能唯一取得所有允许输出的正文；缺配置时构建、诊断、产物及复制入口状态一致，不产生不可解析的绝对地址。
- **置信度**：高，产品对外消费契约缺口。**阻塞**：F12/P4 对外交接；不否定 P1 静态站价值。

### [P2] F-06 · G1 的新用户成功率没有进入终验

- **复核条件**：G1 → 验收 → UAT → 终验期完整；招募方式、执行脚本由测试计划决定。
- **置信度**：高，全文追踪核对。**阻塞**：完整上手体验终验交接。

### [P2] F-07 · G2 的 CWV “良好”目标超出 WORK-N1 的验收范围

- **场景与问题**：参考站在本地移动模拟中达到 LCP/CLS 阈值后，仍不能据此验收完整 Core Web Vitals“良好”。INP 未承接，评估范围也不同。

- **最小修订**：明确选择“借用 LCP/CLS 良好阈值的本地性能验收”，同步 G2 措辞；或保留完整 CWV 目标并承接 INP 与评价口径。无需因此新增内置统计或运行时外部服务。
- **复核条件**：目标、指标集合、观察/验收性质和测量范围一致，不用两项本地通过替代整套 CWV 结论。
- **置信度**：高，官方定义与文内承诺对照。**阻塞**：G2/N1 的性能验收。

### [P2] F-08 · 性能数值的业务时钟和测量合同需要冻结

- **定位**：[PRD](PRD-DOCS-SSG.md):165–168（参考环境）、372（输入后搜索）、595–608（N1）、618–629（N2）、782（Q5）。
- **场景与问题**：演示“加载完成后 1 s”未区分文档 load 与 wasm/水合完成，后者作起点会掩盖等待；搜索从“打开”到首个结果计时，却以用户输入触发结果，任意输入停顿都会影响判定。“默认节流”和“压缩后 100 KB”也未冻结可复核口径。相同产物可因选择不同起点或默认配置得到相反结论。
- **证据**：上述 AC 的触发语义与时间边界未定义；§7.5 把测试方法交给测试计划不能替代产品先确定何种等待/体积算达标。
- **最小修订**：定义演示和搜索的起止事件，分开首次资源加载等待与用户输入后的响应；明确冷/热缓存、参考设备与节流配置、体积压缩口径、参考内容规模和样本通过规则。数值仍是 Q5 的提案，可用 PoC 校准；工具、造数及脚本留给下游。
- **复核条件**：不把交互就绪事件同时作为等待起点；搜索不计任意用户思考时间；给定同一合同能一致判断通过。
- **置信度**：高，验收边界歧义。**阻塞**：N1/N2 的性能计划与终验；未有 PoC 本身不是缺陷。

### [P2] F-09 · 禁脚本、加载中与加载失败不能共用恢复指引

- **定位**：[PRD](PRD-DOCS-SSG.md):138（S4）、156–157（演示/搜索 UI）、274、283（F5）、372–386（F9）、820–825（UAT-4/5/9）。
- **场景与问题**：脚本已经开启而 wasm 尚未加载的读者，按 S4 仍被告知“需要启用脚本”，无法理解下一步。搜索只有无结果/无脚本等状态，没有索引或初始化失败后的可行动恢复状态；网络/加载失败不能伪装成无结果或持续等待。
- **证据**：S4 明确把禁脚本与加载未完成合并；UAT-4 却只覆盖禁脚本。§2.4 已有演示的泛化失败与重新加载要求，F5/AC-4、UAT-9 具体覆盖的是交互中错误，不能据此断言演示完全没有失败设计。现有 [loader.js](../web/loader.js):38–45、128–130 存在异步下载/编译/初始化链，仅作为这类状态真实存在的源码参照，不作为新交互岛已支持失败恢复的证明。
- **最小修订**：禁脚本显示启用说明；加载中显示等待且避免误操作；资源/初始化/水合失败显示失败及重试或重新加载入口。搜索明确加载失败与无匹配的区别。将已有演示失败要求映射到加载失败场景的 AC/UAT，并维持正文、源码、普通导航可用。
- **复核条件**：三个状态有不同且真实的反馈与下一步；失败不显示搜索无结果，不留下可点击但无反应的控件。
- **置信度**：高，状态合并及验收遗漏可定位。**阻塞**：P2 交互岛与 P4 搜索体验交接。

### [P3] F-10 · 将现状调查的范围限定到实际产品运行路径

- **定位**：[PRD](PRD-DOCS-SSG.md):43（E8）、45（E10）。
- **场景与问题**：框架维护者依据“全仓没有任何地方读取 prefers-color-scheme”“仓库里没有 Markdown”选择复用能力时，会把参考/供应商代码与 SDK 生产能力混为一谈。产品需要新增系统主题选择与 DOM 文档管线的判断仍然合理，但全仓断言不真实。
- **证据**：[vendored tweakcn 配置](../examples/theme-studio/vendor/tweakcn/source/config/theme.ts):129 读取系统色彩模式；[Makepad widgets](../makepad/widgets/src/lib.rs):99、243 导出 markdown 模块。文件存在不证明当前 DOM 文档产品能直接复用这些能力。
- **最小修订**：改为当前 SDK/示例运行路径未提供系统主题选择，以及已查 DOM SDK、组件与 xtask 没有适配本产品的 Markdown 内容管线；说明调查范围，保留真实增量。
- **复核条件**：生产能力、vendored/参考资料与调查范围分清，不扩大 Makepad 范围。
- **置信度**：高。**阻塞**：否，可与事实修订一并处理。
