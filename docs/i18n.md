# Languages, formatting and text

Two languages ship with this release: English and `zh-CN`. What that means
precisely is worth stating, because "supports two languages" usually hides the
interesting half.

## What the SDK translates, and what it does not

The SDK ships the words it puts on screen **on its own account** - the label on
a retry control, the word for closing a layer, the sentence a refused clipboard
shows. Those are `rustify_ui::Message`, and every one of them exists in both
languages; a test fails if an arm was filled in with the other language's words
or left the same in both.

Everything else is the application's. An SDK that shipped an application's
vocabulary would be translating words it cannot see; an application that had to
translate the SDK's would find out which ones exist by meeting them in
production.

```rust
let locale = rustify_ui::provide_locale(Locale::Chinese);
// …in a view, tracked: changing the language re-reads it.
locale.text(Message::Retry)
```

Switching changes one signal. Nothing reloads, no component is rebuilt, and
there is no cache anywhere that could hold the old words.

## Choosing the language

`Locale::from_tag` matches on the language subtag, so `zh`, `zh-CN`,
`zh-Hans-CN` and `zh_TW` are all Chinese. Refusing `zh-Hans` for not being
`zh-CN` would be refusing a reader their own language over punctuation.

`browser_languages()` returns `navigator.languages` in the browser's preference
order and `Locale::best_of` takes the first one this SDK has, falling back to
English. Neither is read automatically: an application that remembers what its
user chose last time must not be overruled by a browser setting, so
`provide_locale` takes the application's decision and nothing else.

## Formatting

`format_number` and `format_date` go through `Intl`, and the options object is
the application's:

```rust
let options = js_sys::Object::new();
js_sys::Reflect::set(&options, &"style".into(), &"currency".into())?;
js_sys::Reflect::set(&options, &"currency".into(), &"CNY".into())?;
rustify_ui::format_number(locale, 1234.5, &options)
```

The SDK formats nothing of its own. Whether a number is a currency, how many
decimals it deserves, whether a date needs its year - those are properties of
what the value *means*, and only the application knows that. Passing an options
object `Intl` rejects throws, exactly as an invalid argument does anywhere else.

## Direction

`Direction` exists although neither shipped language is right-to-left. The
components are written in logical properties (`ms-`, `start-`, and so on rather
than `ml-`, `left-`) and the scope root carries a `dir`, so direction is a value
the layout already reads rather than a rewrite waiting to happen. Adding a
right-to-left language would be adding a catalogue.

Inside a GPU region, direction and shaping are Makepad's: the region draws
bidirectional text through its own layout, and the SDK does not reorder
anything on the way in.

## Fonts, and the glyphs a font does not have

The theme's default family is Latin-only on purpose. The faces that cover CJK
and emoji are about 30 MB together, and most applications never draw one of
their glyphs, so they are fetched when a value needs them and not before: a
label whose text is not ASCII moves to the wider family, which is what fetches
those files.

- **In the DOM** this is `font-display: swap` and a system fallback stack. Text
  is readable while a face is on its way.
- **In a GPU region** a font that does not arrive is reported as
  `ErrorKind::AssetLoadFailed`, the region falls back to its built-in Latin
  face, and text it cannot draw shows the missing-glyph mark -
  `Message::MissingGlyph`, which is the box character *and a sentence saying
  whose fault it is*, because a lone box tells a reader nothing.
- When the font does arrive, layout and hit testing are recomputed. A control
  whose label got wider is still hit where it is drawn, not where it was drawn
  before the font landed.

## What is not provided

Machine translation, plural rules, message interpolation with gender or case,
and locale-aware collation are not part of this release. An application that
needs them should use a message library and hand the SDK only the two
languages' worth of its own words.
