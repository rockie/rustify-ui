全部扣分差距如下；严重度、可挽回分相同，先列状态表达问题。

1. **新-1｜P2｜视觉｜可挽回 0.5 分**
   
   **位置：**`U3-ColorField-invalid-1440-light.png`，State 选择区下方的颜色输入整行。  
   **现状 → 规范期望：**字段显示有效外观的 `#336699`，预览本体仅以红框表示 invalid，旁边没有错误原因或修正提示；上方 `State: Invalid` 是演示配置，不能解释这个业务字段为何有误。G-2 要求控件具有帮助和状态，且“不只用颜色反馈”；U3-1 要求 invalid 可区别。  
   **具体修法：**给这个错误示例增加紧邻字段的文字错误说明，明确错误原因与下一步操作，并关联到实际编辑元素；保留现有错误边框。不要把所有未完成 Draft 都解释为最终提交错误。

2. **新-2｜P2｜交互状态｜可挽回 0.5 分**
   
   **位置：**`U3-TextField-s2-surface-1440-light.png` 中部 `Example` 输入行，以及同组 TextArea、NumberField、ColorField 的试验输入区域。  
   **现状 → 规范期望：**字段与上方通用说明之间没有字段本身的可见标签或格式帮助；`Component` 标签属于组件选择器，无法替代试验字段的标签。U3-1 要求字段标签、名称、帮助指向编辑元素，G-2 要求控件具有标签与帮助。此处只确认可见标签缺失，**不推断其 accessible name 或 DOM 关联也缺失**。  
   **具体修法：**在试验字段旁增加简短可见标签，数字/颜色字段提供对应格式或操作帮助；标签与说明关联实际输入元素，保留目前简单的排列方式。

不扣分建议：

- `NumberField-cancel`、`ColorField-cancel` 已显示值恢复，但下方 `Commit / cancel event` 仍为 `—`。若该读数用于解释本次操作，建议回显“已取消并恢复接受值”，或说明它统计的事件范围，避免读数与实际操作看起来脱节。
- consumer 的 `Find`、`Hint/Optional` 局部颜色和 `CustomSpacing` 紧贴输入值属于插槽及 utility 覆盖演示。现有记录没有给出相反目标，未将这些有意定制扣分。
