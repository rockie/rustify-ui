## 1. 确认问题

### [P2] F-01 · 统一旧站产物兼容承诺与共享脚本的改动路线

- **定位**：§0.1 NFR-4（L82）、D13（L113）、§3（L256）、§5.6（L469–481）、§7（L571）、V-3/V-11（L640、648）；关联 T-4。
- **问题**：计划要求没有 [landing] 的站点输出逐字节不变，同时要求修改全站共享的 site.js。现有生成器无条件发布并引用整份脚本的内容指纹，所以普通站点重建时，脚本内容、文件名、每页 HTML 引用及 manifest 都会变化。这两项承诺无法同时实现；实施者仍须重新决定兼容边界或脚本组织方式。
- **证据**：[generation.rs](../../crates/rustify-docs/src/generation.rs) L28–30 嵌入脚本，L881–905 计算指纹并设置全站地址，L1462 无条件发布；[shell.rs](../../crates/rustify-docs/src/shell.rs) L513 每页引用；[publish.rs](../../crates/rustify-docs/src/publish.rs) L60–78 根据文件路径与内容计算 manifest。现有 [generate.rs](../../crates/rustify-docs/tests/generate.rs) L157–168 只比较同一实现的两次生成，不能证明改动前后的旧站产物不变。
- **最小修订**：若沿用修改 site.js 的路线，将兼容目标明确为既有功能与严格 CSP 不变，说明共享脚本及其指纹引用允许变化，并同步 NFR-4、§3、§7、V-3/V-11。若必须保留全产物字节不变，则应定义只在落地页加载的独立脚本，并调整 D13；不能继续同时保留两项承诺。
- **复核**：改稿后兼容目标、机制与验收必须相同；保留字节承诺时，增加固定旧基线与新版对同一输入的实际对比，不能拿两次新版生成代替。
- **置信度**：高，来自完整的指纹发布与引用链。**阻塞**：涉及关键兼容 NFR，须在冻结脚本交付路线、推进 T-4 前解决。

### [P2] F-02 · 从 CSP 来源契约中移除不能表达的 IPv6 字面量

- **定位**：D6（L106）、§5.1 校验规则（L329–330）、§5.2（L347–354）；关联 R-4、NFR-2、V-1。
- **问题**：D6 明确接受回环主机 [::1]，而 §5.2 将该语法与匹配规则称为 CSP3 host-source 的子集。http://[::1]:4211 不能按该 CSP 来源语法表达；按计划接受配置并返回 allows=true，不会使浏览器放行。外部脚本自动合并 origin 的 D5 同样受到影响。
- **证据**：2026-10-21 读取的 [W3C CSP3 §2.3.1 来源语法](https://www.w3.org/TR/CSP3/#framework-directive-source-list) 中，host 字符不包括 IPv6 所需的方括号和冒号；[§6.7.2.10](https://www.w3.org/TR/CSP3/#match-hosts) 也没有提供字面量 IPv6 的匹配承诺。本项依据规范原文，未声称做过本期 IPv6 浏览器实测。
- **最小修订**：来源及脚本自动提取的 origin 统一拒绝 IPv6 字面量；本地替身继续用 localhost 或 127.0.0.1。无需为此增加 URL 依赖或服务。
- **复核**：V-1 同时覆盖显式来源和外部脚本 URL 的 IPv6 拒绝路径；保留的回环来源在实现后的浏览器检查中验证。
- **置信度**：高，配置承诺与规范语法直接冲突。**阻塞**：M1 的来源校验及匹配契约；应在相关实现前修订。

### [P2] F-03 · 补上新表单 URL 角色在最终产物检查中的兼容处理

- **定位**：D9（L109）、§5.5（L442、452、463–467）、T-3（L696）、V-6（L643）；关联 R-5、NFR-4。
- **问题**：计划只让非落地页表单产生 form-blocked 警告并保留原值，但新增 FormTarget 后还会进入既有的最终产物引用检查。例如普通文档中的 form action="/api/lead"，今天不按静态文件引用处理；照计划添加 URL 角色后，该站内端点不在输出中，会在另一道闸门报 output-check 错误。跳过 check_document_under 的表单检查不能阻止这条消费链。
- **证据**：[html_check.rs](../../crates/rustify-docs/src/html_check.rs) L68–81 当前没有表单角色；L727–760 按 url_role 记录 URL 槽位，L537–541、580–583 把槽位交给 document_references；[generation.rs](../../crates/rustify-docs/src/generation.rs) L699、721–792 消费全部槽位并要求站内目标存在，未区分表单目标。计划未把这处消费者列入处理设计。
- **最小修订**：在 §5.5 和 T-3 明确 FormTarget 在 final_documents 中的行为。可从通用链接/资源存在性循环排除该角色，保留落地页 resolve_references 对站内表单目标的校验；若要求最终树再次校验落地页表单，应传入页面类别，仅跳过普通页。不能取消落地页校验。
- **复核**：V-6 增加完整生成回归：普通页指向不存在的站内端点时仅警告、生成成功且 action/formaction 原值不变；落地页指向缺失站内目标仍失败。[content.rs](../../crates/rustify-docs/src/content.rs) L3037–3088 的 resolve_html_link 可继续承担已选定的页面级校验。
- **置信度**：高，已追通新增角色到现有消费者，architecture 另行复核。**阻塞**：M3/T-3 的兼容设计。

### [P2] F-04 · 厂商在线验收须证明脚本确实执行了预期行为

- **定位**：A-1/A-2（L93–94）、§5.8（L517–519）、V-13（L650）、M5（L686）；关联 R-9。
- **问题**：V-13 使用测试 ID，仅要求脚本 HTTP 200、没有 CSP 违规及记录实际请求域名，没有要求获得可执行的非空脚本，也没有要求发生统计请求。空响应或初始化未执行都可能满足这些判据，不能解除 A-1/A-2。
- **证据**：主 agent 于 2026-10-21 用 Python urllib.request.urlopen 分别只读 GET [全零测试 ID 的百度 hm.js](https://hm.baidu.com/hm.js?00000000000000000000000000000000) 和 [另一测试 ID](https://hm.baidu.com/hm.js?0123456789abcdef0123456789abcdef)，两者均为 HTTP 200、Content-Type: text/plain; charset=utf-8、响应体 0 字节。architecture 独立请求得到同样结果。因此“200 且无违规”确有空通过路径，不是对厂商行为的猜测。Google 脚本能下载也只证明取到文件，不能证明自托管初始化已经驱动请求。
- **最小修订**：V-13 要求非空脚本、没有初始化运行错误，并观察到本次配置应触发的统计请求；记录实际域名及相关 CSP 结果。百度应写明需要可运行且获授权的测试站点 ID，未取得时保留 A-2 缺口。验收只要求请求实际发起，不扩大到广告平台计入转化。
- **复核**：空响应、没有统计请求、初始化报错均不能通过；A-1/A-2 的结论只覆盖实测触发的厂商功能。更新后的文档示例再次执行 V-8 和相应 V-13。
- **置信度**：高，有可复现的只读 HTTP 证据。**阻塞**：M4 示例定稿与 M5 厂商验收；不阻塞独立框架代码开发。

### [P2] F-05 · 拆开有 JS 与无 JS 的表单成功断言

- **定位**：V-7（L644），与 NFR-5（L83）、§6（L553）、初始化脚本定义（L634）冲突；关联 R-5、NFR-5。
- **问题**：V-7 对 JS 开、关两次提交共同要求“303 → thanks/ 加载并上报 conversion”。关闭 JS 后 init.js 和追踪脚本不执行，原生表单可以完成，但不会上报 conversion；该退出条件无法成立。
- **证据**：同一计划的 §6 已明确无 JS 时追踪不生效；L634 规定 conversion 由 init.js 检测感谢页元素后推入队列。这里是验收断言互斥，不是要求实现绕过用户禁用 JS 的设置。
- **最小修订**：JS 开时验证 gclid 提交和 conversion 请求；JS 关时验证原生 POST、303、感谢页内容完整，并确认没有脚本追踪请求。
- **复核**：两个独立浏览器上下文分别覆盖上述成功结果，与 NFR-5 和 §6 一致。
- **置信度**：高，原文的机制与断言直接矛盾。**阻塞**：V-7 及对应里程碑退出检查。
