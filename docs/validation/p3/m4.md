## F24: why the scene presented on every second frame

M1 measured 0.5 presentations per drive under both a software rasteriser and a hardware one, which is what said this was the pipeline rather than the rasteriser. The phase, once traced:

1. The page drives the camera inside its own animation frame callback. Leptos runs the effect on a microtask; `apply` queues the work and asks the host for a pump; the pump runs on a further microtask. All of it is still inside frame **N**.
2. The pump applies the props, the widget redraws, and Makepad ends the pump by asking for an animation frame. `requestAnimationFrame` called during frame N's callbacks schedules frame **N+1**.
3. At frame N+1 the page drives again first. Its props pump asks for an animation frame too - but `req_anim_frame_id` is still set, because Makepad's own callback for this frame has not run yet, and the request is dropped as a duplicate. Makepad's callback then runs and draws.
4. At frame N+2 the page drives, the request is now free to be made, and it schedules frame N+3. Nothing draws in frame N+2.

So two requests fall in one frame and the next frame goes by unpainted: one presentation per two drives, in any environment, at any speed.

The fix is four lines in `embedded.js`: after a props pump, if the region asked for an animation frame, cancel it and serve it here - append `ToWasmAnimationFrame` and pump once more. That pump is still inside the task that changed the props, so its drawing lands in that frame's paint. A request made *during* that draw is a genuine next frame (an animation running on) and goes back to the browser untouched, so nothing loops and no animation starves.

Measured after, in the page: **53 presentations for 54 drives** over three seconds, against 35 for 71 before. The clause NFR-1 is written with - a driven frame is a drawn frame - now holds, and M8's `budget-data` is where it becomes a gate.

M1's probe 2 runs on every build, so it re-measured the same scene on this one. Both halves of it changed, because both the halving and the oversized pane were fixed:

| --- | --- | --- |

## What the checks found

**The pane was wider than the window.** 1,964 CSS pixels of canvas in a 1,440 pixel viewport. A canvas is a replaced element, its width and height attributes are its intrinsic size, and the host writes those attributes from the size the canvas ended up at: as a flex item along its own main axis, `min-width: auto` held it at its intrinsic width, which then grew again the next frame. M2 met the same rule in the other direction - a strip that would not be thirty-two pixels tall - so both sizes are now stated and both minimums zeroed. The scene had been drawing nearly twice the objects it needed to, which is also why M1's frame figures were as slow as they were.

**A form only ever saves once.** `FormState::submit` sets `submitting`, and only `form.submitted(result)` clears it; a synchronous save that never reports leaves the button disabled forever. The table's details form had the same defect since M2 and its checks never caught it, because they only ever saved one row. Both forms now report, through a handle the form is put into after it is built.

**The chosen list moved the scene under the pointer.** Every click added an entry, the list grew, the pane went down, and the next click landed somewhere other than where it was aimed - which showed up as a box that took the row above the one it was drawn around. The list's height is now stated. The checks also measure the pane again before each gesture, because a test that trusts one measurement is a test that will find this again the next way it happens.

**A stride into a span is not a scatter.** Sampling points with `step * 137 % 1096` visits eight distinct columns, and the scene's two layers are 130 pixels apart: a hundred sampled points never landed on an upper-layer object, so the rule that decides between two layers was never checked. The sample points come from a generator now, and the check asserts that some of them are on the upper layer before it uses any of them.

## Deviations from the plan, and why

- **`SceneRegion` has no `layout` prop.** §2 listed `layout: Arc<Vec<SceneRect>>`. Where an object is has been arithmetic on its index since M1; handing the region a table of ten thousand of them would be the same formula written twice, and the region would have to be told again every time one was renamed. It gained `labels` instead - only the objects a person renamed are in it.
- **The modifier travels with the action.** §5.4 said the application merges or replaces "by the modifier key". Which one it is, is a fact about the moment the pointer went down; an application reading the keyboard a turn later reads a different moment. So `Marquee` and `Pick` carry `additive`.
- **A click is a box that did not move.** Both start on an object, and only the distance travelled tells them apart. Deciding at the start - a click is a press with no drag - is not something the press can know.
- **The text shaper's cache was not parameterised.** §10's M4 row makes that conditional on probe 2 asking for it; it did not, and the pane now culls to a window less than half the size M1 measured against.

## What serving the frame in place cost

B1's latency moved from **41.7 ms** (M3) to **44.9 ms**, against a 50 ms gate it still passes. The draw that used to happen in the browser's own animation frame callback now happens inside the task that changed the props, so the work that was on the other side of a yield is on this side of it - which is the whole point, and it is not free. Cold start moved 154 -> 178 ms and hot 143 -> 172 ms over the same three runs; those two are against gates of 5,000 and 2,000 ms and the movement is noise beside them.

The number to watch is B1. There is 5 ms of headroom, M8 is where it becomes a gate, and if it turns out to be tight the lever is to serve the frame only for the region that asked for it in this task rather than at the end of every props pump.
