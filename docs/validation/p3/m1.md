### Probe 3 in detail

- Two instances of one module: `bindgen.js` evaluated a second time under `?instance=2`, one `WebAssembly.Module` shared, two linear memories. One wasm request, two glue requests.
- A trap through an export call reaches the instance it happened in. The caller still sees the `RuntimeError`; a later call gets `InstanceDead` rather than a second trap.
- The other instance took **100 of 100** actions afterwards, and again after the handler trap.
- A trap inside a Leptos event handler **was attributed to its own instance** by the glue URL in the uncaught error's stack. The D15 fallback (a handler trap taking the whole page down) is not needed.
- After one restart the dead instance's linear memory is **still reachable** after `HeapProfiler.collectGarbage`, as ADR-8 predicted. The figure measured here is 2.6 MB because the instance that died had a scope with no region; a full B0 instance starts at about 40 MB (P2), which is what the cap in D14 is about.

## What the probes found that the plan did not ask

Driving one camera position per animation frame, the scene presented on **every second frame** - 0.5 presentations and 1.5 pumps per drive - and the ratio was the same under SwiftShader (401 drives, 602 pumps, 201 presentations) and on hardware (1201 drives, 1801 pumps, 600 presentations). Identical ratios in a software rasteriser and a hardware one make this a property of how a props application reaches a draw, not of what either rasteriser can do.

Two consequences:

- The p95 intervals above are two frame periods in both environments. Headed Chrome holds because its display runs at 120 Hz; at 60 Hz the same pipeline would present at 30 Hz.
- §7's clause "effective frames ≥ drives × 0.99" cannot be met while this stands, in either environment.

This is M4's to resolve, with M8's gate as the check, and it is recorded in the plan's risk table rather than only here. It does not change A-3's answer: removing the halving would put headless at about 25 ms, still over the 20 ms budget.

## Deviations from the plan, and why

- **The frame count is taken in `embedded.js`, not in the fork.** `FromWasmBeginRenderCanvas` is dispatched on the embedded region object, so overriding it there counts the same presentations without touching `makepad/platform/src/os/web/`. The fork is still where M6's byte ledger goes. Plan §1.2 updated.
- **The scene's extent is 13,050 x 3,996, not 13,000 x 4,000.** The round figures in §3 do not follow from the layout formulas; the exact bounding box does, and a camera clamp has to be exact. Plan §3 updated.
- **The camera is driven through an export rather than by wheel events.** The input path is M4's. What A-3 asks is whether a rasteriser can draw a window of B3 inside the budget, and the draw is the same draw either way; M8's gate drives the real path.
- **Only the API with a caller was written.** The sample's insert, delete and write, the scene's marquee and pick, and the sort's progress are M2 to M4's, and they arrive with the code that calls them.

## One assertion that was wrong, and the behaviour behind it

The first version of the boot check asserted that a clean start records no error-level diagnostic. It does record one: Makepad names its window as a region starts, the embedded contract refuses a region the document title, and the refusal is recorded. That is the contract working and `docs/compatibility.md` has said so since P2's M7 - every region on every example does it. The check now allows `UnsupportedCapability` and nothing else.
