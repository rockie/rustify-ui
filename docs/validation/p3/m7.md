## The four faults, and what each one may cost

| Fault | How it is injected | What it costs | What must be true afterwards |
| --- | --- | --- | --- |
| A font that does not arrive | `serve --fault missing:` on the Latin face, one document per occurrence | the glyphs a region would have drawn | the runtime starts, both halves still move one value, and the file is named in the record with what to do |
| An answer that arrives after a newer one | two loads started 380 ms apart, answered in reverse | nothing | the newer answer stands, and the confirmed state is the one from before either was asked |
| A scope closed from inside a region action | the application closes its own scope in the callback a click delivered, while the pump is still on the stack | the scope, deliberately | the runtime is alive and unfailed, no region is left, and a new scope takes an action and reports it |
| A GPU context lost and given back | `lose_context` / `restore_context` on the region's canvas | the pixels, until the rebuild | every confirmed value is still the application's, the region is `lost` and then `ready`, and each loss is recorded once as something to do nothing about |

"Confirmed" is what the application accepted and reported, read from the page's own snapshot rather than from a control: a fault may cost a frame, a context or an answer without costing one of those.

## What the checks found

**A two-minute endurance run measures a cache filling.** The first version warmed up with 2,200 rounds and then measured; at two minutes the memory curve climbed the whole way, and it passed only because 1% of 75 MB is larger than what it climbed in the last quarter. A ten-minute run showed the shape: it rose for six minutes and was then flat for four. Every label these regions draw is a string they have not drawn before - the count is in it - so what was growing was the shaper and layouter caches on their way to their four thousand entries. The warm-up is 5,000 rounds now, which is past that point, and a four-minute run after the change moved **zero bytes**. This is the phase-two lesson again (P2 M10, `docs/plan/P3-WASM-UI.md` §12) in a fixture whose strings never repeat.

**A scope that closes does not take the application's objects with it.** The closure check first asserted that a new scope starts at the first object, which is what the single-shot phase-one check sees. It is only true the first time: the objects live in the application, not in the scope showing them, so round two starts wherever round one left off. The expectation is now the one that is actually true - the object count is unchanged and a new scope takes an action and reports it - which is a stronger statement than the one it replaced.

**The application refuses a name another object already has.** The diagnostics comparison runs the same thousand actions twice, and half of them rename an object. The second run asked for names the first had used, the application refused them, and the driver saw an action that never arrived. Each run now tags its own names. The refusal was correct; what was wrong was a check that assumed nothing remembers the last run.

**A switch that answers with what it replaced is not a switch that failed.** `set_diagnostics` returns the previous value, so turning the record back on answers `false`. Asserting on the return value made the check fail on a page that had done exactly what was asked; it now reads the record's own `recording` flag.

**Two hours of growth is two hours of nothing, spent in the first three quarters of an hour.** The curve is sampled every ten seconds, 720 points per instance. Instance 1 rises in nine steps and instance 2 in five; seven of instance 1's are single 64 KiB pages, and both instances take the same two large ones - 3.54 MB at minute 40 and 1.97 MB at minute 43. After that point neither moves again: **flat for the last 77 minutes**, 0 bytes across the last quarter. What the gate asserts is the last quarter, which is the conservative reading; the honest description of the whole run is that allocation stops at minute 43 and the remaining hour and a quarter is a steady state.

**The hundred-mount-round check is sensitive to what ran before it.** The first full sweep of this milestone was started straight after the two-hour endurance run and `m8-baseline.spec.ts:102` failed in it - the only red in 135 tests. Re-run on a machine that had not just spent two hours at ten actions a second, the same check passes, and so does the rest of the project. Nothing in the tree changed between the two runs. The lesson is about scheduling rather than about the product: a growth check reads the machine as well as the build, and the gate runs (`budget`, `budget-data`) already have D13's rule for this. The 2 h run should be the *last* thing a session does, not the thing it does before the regression sweep.
