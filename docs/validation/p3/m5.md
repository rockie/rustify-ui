## The four doors, and why there are four

A trap under `panic = "abort"` is an `unreachable` in wasm. Where it is seen from depends on what was on the stack:

| Door | Who sees it | How it is attributed |
| --- | --- | --- |
| An export the page called | the caller | the loader's call boundary, which reports before it rethrows |
| A task the host was running | the runtime, inside its own `try` | directly |
| A DOM event handler | nobody - the browser dispatched it | the glue URL in the uncaught error's stack; each instance has its own |
| The page simulating one | itself | directly |

All four have to arrive at the same notice, or the three real ones are being checked against a door nobody else uses. They do.

## What the checks found

**The failure notice was addressed to instance 1, not to the instance the page was showing.** After a restart the page's instance is number 2, then 3; the notice's own gate still said "only tell the page if this is instance 1", so the second failure was silent - the page sat there looking alive with nothing mounted in it. Found by the third round of the restart check. The page now tracks which instance it is showing, and a restart moves it.

**A dead instance's record cannot be read through the door the page uses.** The check that compares two instances' diagnostics asked the dead one for its record afterwards and got `InstanceDead` - which is the call boundary doing exactly what it exists for. The check now reads it before the trap. Nothing was wrong with the code; the check was asking the wrong way round, and a check that had been written the other way would have looked like it passed.

**The teardown check's warm-up was no longer long enough.** It mounts and unmounts a scope 150 times, samples, does 100 more, and asserts linear memory did not move. It moved by 17,956,864 bytes. The curve says why: flat, then three steps, the last at about round 210, and then flat again for the 350 rounds after it - the working set had not finished filling by round 150. Three runs produced byte-identical curves, so this is where this build puts it rather than run-to-run variance, which is what the check's own comment had assumed. The warm-up is now 300 and the comment says what was measured. **This is a changed assertion in an existing check, and the reason it changed is that M5's per-mount work shifted where the allocator settles - not that anything leaks.** Six hundred rounds add nothing after round 250.

**A region that asks three times records three refusals.** The check for "a region denied a GPU context keeps its DOM half working" expected two host errors for two regions and now sees six. The host records what it saw; the record the application reads tells the three apart, because two of them are `GpuInitRetry` (informational) and only the last is `GpuInitFailed`. The assertion was updated to six and says why.

## Deviations from the plan, and why

- **The abort controller lives in the host, not the loader.** §5.5.3 fixes the order a dying instance releases things in, and `abort()` is first. `enter_fatal` is in `embedded.js`, so that is where the controller has to be for the order to be the one written down; the loader now registers its own two listeners with `hooks.signal` like everything else. The signal reaches Rust through a getter on the hooks object.
- **`defer_after` is new on the host contract.** §2 does not list it. A retry has to wait 250 ms, and D15's rule is that the host owns anything holding a wasm callback so a trapped module is not re-entered - which `defer` already says for a turn and now says for a wait. A failing runtime clears the timers along with the posted messages.
- **The GPU retry's browser-side check lives in the existing fixture.** V5 lists three GPU start failures under M5. The injection fixture - a canvas that answers `null` for `webgl2` and for nothing else - has been in `m7-recovery.spec.ts` since P2, so the retry assertions were added there rather than built a second time. It still checks the same three things: two retries, one failure, and a notice inside two seconds.
- **Two examples had no policy check at all.** §10's M5 row asks for zero CSP reports on all four. The workbench and the data example already had one inside a larger check; `p3-policy.spec.ts` is the same check for the other two, and it runs in both projects from one file.
- **`boot_instance` takes the fixture to mount.** An instance that is going to be asked whether it still works needs something to work; one that is going to be killed needs a way to die. It mounted only the trap fixture before.
