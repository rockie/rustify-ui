Date: 2026-09-12. Machine: macOS 26.6.2 (Darwin 25.6.0), Apple Silicon, rustc 1.97.0-nightly (2026-05-19), Node 26.1.0, Playwright 1.63.0 (bundled Chromium, SwiftShader WebGL).

Delivered. A hundred thousand rows can be put in order, filtered down and searched through without the page stopping, and a write that lands in the middle of any of that throws the answer away rather than reading a row that has moved.

Both are measured values, not gates: the gates are M8's, on their own project. There is about four times the headroom on the sort, which is close to what M1's probe predicted (p95 57 ms for the sort alone, against 114 ms here for the sort plus building the view and redrawing the table).

## Deviations from the plan, and why

- **`Job::start(requests, version, work) -> Ticket` became `Job::new(...)` plus `job::run(...)`.** The ticket goes into the job, which is where it is checked, and nothing useful can be done with a copy of it outside: what makes a request current is its sequence, not who is holding it. Splitting the state machine from the thing that drives it is also what makes the rules checkable without a browser - every rule in the module has a test that steps a job by hand.
- **Cancelling is `Requests::cancel()`**, one line in `task.rs`: issue a request and drop it, so the one that was current stops being current and the sequence it lost to belongs to nothing. The plan named an explicit cancel without saying where it lived.
- **`Budget::exhausted(rows)` became `did(rows)` plus `exhausted()`.** Work that finishes in the middle of a batch never reported its last rows, so a progress bar stopped a few hundred short of the end every time. Reporting and asking are two things.
- **Two files the plan's list did not have**: `src/scan.rs` (what a filter, a group and a find ask of a row) and `src/view.rs` (which rows are shown, and what an insert or a delete does to that). Both are arithmetic, both are the kind of arithmetic that fails quietly, and both are tested on the host beside `sort.rs`, which is where the plan put the sort for the same reason.
- **`DataTable` gained `sorted` and `on_sort`.** §10's M3 row asks for sorting by column heading; §2's component row did not list the props it takes. A heading with `on_sort` is a real button inside the `columnheader`, so it is reachable by keyboard, and every sortable column carries `aria-sort` - `none` when it is not the sorted one, because a sortable column that says nothing cannot be told from one that does not sort.
- **A sort sorts the view; a filter replaces it.** §5.2 says both, in those words, and the consequence is worth stating: filtering after sorting loses the sort, and sorting after filtering keeps the filter. A find is asked of the view, because where it lands is a place in what the person is looking at.
- **The status line is about the newest job only.** Four sorts started in one turn end three times before the fourth takes a slice, and without this the line would say "cancelled" while a job was running. Each ending is still recorded as a diagnostic; only the newest one is the news.

## What the checks found

**A cancelled older job was overwriting the status of the newer one that replaced it.** Found by the check for "only the newest of several jobs takes effect", which polled for "no job running" and read the first cancellation. Fixed by numbering the jobs.

**Digits sort before letters.** The sample's alphabet is written `A-Z0-9`, and it is easy to read that as an order. It is not: the comparison is over bytes, and `0` is `0x30` against `A`'s `0x41`. A check that edited a cell to all `A`s and expected it to sort first was wrong, not the sort.

**A write driven from the test process arrives whenever the round trip gets round to it.** The three "a write during a job" checks were passing and failing by luck depending on whether the sort had finished first. They now start the sort, wait inside the page until it has done a slice, and do the write there - and each of them asserts that the job really was still running when the write landed, so a check that passes for the wrong reason fails instead.
