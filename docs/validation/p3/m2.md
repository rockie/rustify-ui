Date: 2026-09-12. Machine: macOS 26.6.2 (Darwin 25.6.0), Apple Silicon, rustc 1.97.0-nightly (2026-05-19), Node 26.1.0, Playwright 1.63.0 (bundled Chromium, SwiftShader WebGL). data-workbench build `6906f8524264c066`, bridge `2906431550179788552`.

## Status

Delivered. A hundred thousand rows are reachable, sixty of them are in the document, and a selection survives a sort and does not survive a deletion. They are the substance of this report.

## What the checks found

Seven, in the order they cost time.

**A redirect tore down a GPU region and the browser lost the context.** Arriving at `/` redirects to `/table`, and the view was chosen by a closure over the location. The closure answered "table" both times - but it *ran* both times, so Leptos disposed the first table and built a second. That destroyed and rebuilt the strip's region within one turn, and the second context was lost before it had compiled a shader: fourteen `compile_fail` lines with a null info log, then `Missing shader`, then the loss. A `Memo` answers "table" once, and the region is built once. This was showing up as an M1 check failing - a clean boot is a boot with no error-level diagnostic, and `GpuContextLost` is one.

**A canvas would not be thirty-two pixels tall.** `flex: 0 0 32px` on the strip gave it four hundred and fifty-eight. A canvas is a replaced element: its width and height attributes give it an aspect ratio, `min-height: auto` on a flex item will not let it shrink below the height that ratio implies, and at the grid's width that is `916 / 2`. The height is now stated, with `min-height: 0`. The table had been giving away half its own height to it.

**The window changed length at the table's edges.** It was a screenful plus overscan either side, except at the top, where the margin above was clipped - so the pool of row elements shrank by ten as you scrolled to row 0 and grew again as you left. Walking to the end of the table with Ctrl+End and back with Ctrl+Home put the keyboard on a slot that then ceased to exist, and the focus fell to the body. The window is now the same length wherever it is, which is what its own comment had always claimed; there is a test that says so at six scroll positions.

**Which row a slot is showing is written later than you think.** It is a reactive attribute, so it is written when its own effect runs, and that can be after the effect that decided to move the keyboard. Two faults, one on each side of it:

- Asking for the cell by `aria-rowindex` found the cell that was there a moment ago, or nothing. The table now finds it by its slot, which is a static attribute, and so is the element that is *about* to carry those indices.
- The focus event that follows was read back by the grid's own `focusin` handler, off the very attributes that had not been written - so the table taught itself that the keyboard was somewhere it had just moved it away from, and stayed there. Focus the table places itself is now not read back.

**The header sat over the wrong column.** It is outside the scroller, and it was offset by the column index of its first drawn column while the body was offset by the scroll position. The two agree only at a scroll of zero, which is where everything had been until the keyboard could reach column twenty. It is now offset by the difference, and the header clips.

**The tree's `aria-expanded` never changed.** The rows are keyed by the group, which is right - opening one keeps the element it has - but it means the element is not rebuilt, and the attribute had been captured at build time rather than read. A screen reader was told every group was open. The children came and went correctly the whole time, which is what made it invisible.

**Two locators in the checks were wrong, not the product.** A number input is a spinbutton without saying so in an attribute, and `TextField` puts its test id on the input itself rather than around it. The check now asks for the element that carries *both* the test id and the role with the name, which is a stronger question than either half and does not care whether the role is implicit.

## Two flaky checks the regression turned up, neither of them M2's

**`cargo test -p xtask` failed about one run in six.** Two tests in `serve.rs` shared one temporary directory named after the process id, they run at the same time, and one of them deletes the tree at the end. Each now has its own. Fifteen consecutive runs pass.

**The catalogue blocks its main thread for six seconds after it says it is ready**, and whichever check happens to be measuring at that moment fails. It moved between runs: first `p2-i18n`'s set-up, whose click on a nav button waited out its own five-second timeout; then `p2-theme`, whose first of twenty theme switches was timed at 6,501 ms against a 200 ms budget.

Measured from inside the page: ready at 39 ms, one presentation at 404 ms, then no animation frame at all between 437 ms and 6,453 ms, and a second presentation at the end of it. That is the region's first draw with text in it - the font arrives over HTTP, the atlas is built, and a software rasteriser takes six seconds over it. Nothing about it is new: **the same measurement on a build of `c5f135a`, without any of this milestone's changes, gives 5,900 and 6,067 ms.** The check passed before because another spec had run first in the same browser process and absorbed it, and this milestone's bigger module changed which spec that was.

So the fix is in the harness, not the product: `waitForReady` now also waits for the page to stop blocking its own animation frames. Quiet is the absence of a *late* frame rather than the absence of frames - a region that is animating is not busy, and one that is rasterising is. `p2-theme` standalone went from failing twice out of two to passing twice out of two, and the whole project passes 46/46 from a cold browser.

A six-second first draw is worth knowing about on its own. It belongs to the catalogue, which is not a load the phase has a budget for; B0's and B2's start-up gates are M8's and are measured on their own examples.

## Deviations from the plan, and why

- **The cells are a pool across as well as down.** §5.3 says columns window "the same way"; they had been keyed by absolute column index, so scrolling sideways destroyed and rebuilt every cell in every row - and took the focused one with it. Keyed by slot, like the rows.
- **`focus_within` is gone from `dom.rs`.** The table no longer finds a cell by selector, and nothing else used it. Only API with a caller ships.
- **`m6-components.spec.ts` and `p2-a11y.spec.ts` join the list of checks the twenty categories reach.** The plan's M2 row named `p2-catalog.spec.ts` and `support.ts`; these two count the same thing from the other two examples. All four now count `CATALOG_SIZE`, and the catalogue's "four with no GPU half" is six: a table and a tree are DOM because semantics is what they are for. §10's M2 row now says four places rather than two.
- **`waitForReady` waits for quiet.** Not in the plan at all; it is the fix for the flake above, and it is in the shared harness, so every project was run again after it.
- **`docs/components.md` and `docs/quickstart.md` say twenty rather than eighteen.** The count is R18's, and it is no longer the catalogue's; both now say which is which. The rest of the quickstart's closing section is M8's.
