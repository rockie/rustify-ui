## What the state machine is for

Three questions, and they are the three every form gets wrong when it writes them again:

1. **Which validation answer is still current.** A field carries a generation; a validation carries the generation it was started for; an answer for a generation the field has moved on from describes a value that is not on screen and is dropped.
2. **Whether a submit that arrived during a validation is still the submit that was asked for.** A waiting request is bound to every field's generation at the moment of asking. A field that changes voids it, because what the user asked to save is not what is in front of them any more.
3. **How many saves twenty clicks are.** One, and the count is structural: the save closure belongs to the form, so the two moments a request can be granted - straight away, or when the last check lands - go through one place.

## Two deviations from the plan, and the reasons

**`FormState` holds no values** (§3, §5.3.1 said it would). The application already holds them - that is what a controlled component means - and a second copy is a second answer to "what is in this field", which is the exact bug P1 spent M6 removing from its controls. What lives in the state machine is the bookkeeping around the values. Rules and saving are the application's functions, called from the state machine at the moments the ordering matters, and this is what lets the workbench apply four of its twenty properties as they are typed (the region draws them) while the other fifteen are a draft a save applies.

**The submit button is `aria-disabled`, not natively disabled** (§5.3.3 said the button's state comes from `can_submit()` while `submit()` stays the authority). Those two cannot both be true of a natively disabled button: the browser never delivers the click, so nothing behind it can judge one. Found by a test that tried to submit while a check was running and got no event at all. `Button` grew an `unavailable` prop for it - announced as unavailable, kept in the tab order where it can say why, click still delivered - and the same shape already serves a menu command that cannot run.

Both are written back into §3 and §5.3.

## What a test found

`submit()` re-runs the application's rules, and it was clearing every error first - so an answer that had come back from an asynchronous check was wiped and the form saved a value the check had refused. Errors now carry who put them there: a rule may withdraw its own on the next ask; a check's answer is about the value itself, which has not changed. `asking_twenty_times_after_an_async_failure_never_saves` is what caught it, and it is the reason the two sources are a type rather than a comment.
