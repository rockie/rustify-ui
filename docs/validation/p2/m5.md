# P2 M5 report: the workspace, and B1

Date: 2026-09-10. Machine: macOS (Darwin 25.6.0), Apple Silicon, rustc 1.97.0-nightly (2026-05-19), Node 26.1.0, Playwright 1.63.0 (bundled Chromium, SwiftShader WebGL), Tailwind CSS 4.1.13.

## Status

Delivered. property-workbench matches the PRD's B1 shape item by item, and the three workspace components are in `rustify-components`.

## B1, item by item

The PRD (§5.2) defines B1 as "3 panels, 10 tabs, 1,000 business objects, 20 visible properties, 1 menu and modal". The plan's rule is that the name may not be used until every item matches, so:

| B1 asks for | Delivered | Where |
| --- | --- | --- |
| 3 panels | 3: the object list, the GPU view, the property form. Each declares its own minimum width (220 / 320 / 360) and a divider stops rather than pushing through one | `Splitter` over the application's own grid |
| 10 tabs | 10 views over one set of objects - all, six colours, locked, archived, recent. Filters rather than folders: switching keeps the selection | `PanelTabs`, `TABS` in `main.rs` |
| 1,000 business objects | 1,000, unchanged since P1 | `initial_objects` |
| 20 visible properties | 20: four applied as they are typed (the region draws them), fifteen drafted and applied by a save, and the read-only id | `details.rs::FIELDS` |
| 1 menu | A context menu opened by right-clicking **inside the GPU region**, anchored to the rectangle that was clicked - which is §6.2's requirement that at least one B1 menu comes from a GPU anchor | `Menu` with `Anchor::region` |
| 1 modal | The command palette is a modal layer: it makes the scope inert, traps focus and returns it. That is the modal B1 asks for, and it is worth saying which one it is rather than counting a layer twice | `CommandPalette` |
| A command entry (§6.2) | Search, run, and commands that cannot run staying visible with a reason | `CommandPalette` |

**B1 is a load definition, not a budget.** A-3 still stands: M8 measures the numbers and compares them with R29/R30, and no gate is claimed.

## What the work turned up

**The splitter cannot contain the panels.** A panel here holds a GPU region, whose application marker is not `Send`, and anything passed through a Leptos component's children has to be. The component was written the obvious way first and would not compile against this example - which is the right time to find out. It draws its dividers over a row the application lays out instead, and owns the arithmetic, the dividers and the keyboard. `docs/workspace.md` says so, because the next person will reach for children too.

**A rounding artefact in the report, not in the code.** The snapshot printed panel sizes to whole pixels, so a row that is exactly 1,160 wide could read as 1,161 and a "the total never changes" check failed on a display detail. A drag moves room between two panels exactly; the report now says so to three decimals.

**A P1 test that aimed at a pixel.** `m5-text` clicked 470 pixels into the
region to reach the notes it draws. B1 gave the region its own panel, the panel
is narrower than the two-column layout it replaced, and 470 is now past the
edge. The region reports where it drew its two pieces of text now, and the test
asks - which is what R25 says to do and what the same test would have needed the
first time anybody changed a layout. It is the third time this milestone series
has found the same shape of problem: a caller guessing at geometry the region
already knows.

**And the correction the region's new report needed.** Reading a widget's
rectangle before it has been drawn is a warning from the platform - an area can
be an instance pointer holding no instances - so a scope disposed while its
region was still starting produced six of them per pump, and a P1 test that
asserts a clean teardown caught it. The guard is `Area::is_valid`, not
`is_empty`: `is_empty` only asks whether there is a pointer at all, which there
is.

Worth recording twice over, because the first two attempts at the fix silently
did nothing: the patches were written against source that `cargo fmt` had
already reflowed, and the build reported an identical wasm size both times. An
unchanged size after an edit is the signal that the edit did not land.

## Not done here

- No arbitrary docking tree and no native multi-window layout: D7, and it stays out.
- The layout is not in the URL and does not persist. A workspace that put its layout in the address bar would fill a person's history with resizes.
- The B1 *numbers* - start-up, transfer size, input-to-paint latency - are M8's. What M5 delivers is the shape they will be measured on.
