# P2 M2 report: eighteen component categories

Date: 2026-09-10. Machine: macOS (Darwin 25.6.0), Apple Silicon, rustc 1.97.0-nightly (2026-05-19), Node 26.1.0, Playwright 1.63.0 (bundled Chromium, SwiftShader WebGL), Tailwind CSS 4.1.13.

## Status

Delivered. All eighteen categories R18 names have a DOM component; eleven of them are also drawn by a GPU region, three more partly, and the four that are not say where they are drawn instead. The capability catalogue moved into the component crate, is printed into `docs/components.md` by a command, and is checked for drift in CI.

## What was imported, and what the rewrite changed

Seventeen Rust/UI component files and one stylesheet arrived verbatim in one commit (`098281e`) and were rewritten in the next (`fe5a37e`), so the change reads as a diff. `sources.lock.json` records each file's origin, the digest of what arrived and whether our copy is still that; `cargo xtask sources verify` fails in both directions - a file still claiming to be verbatim that has changed, and one claiming to be rewritten that has not.

Four things the rewrite had to change, none of them cosmetic:

- **Nothing was controlled.** `Switch`, `Tabs` and `RadioGroup` each held their own state in an `RwSignal` with no way to report a change, so two of them bound to one value could disagree. Every control here shows what the application holds and asks for the rest, with `disabled` and `read_only` as signals.
- **Four components could not run under the release policy.** Dialog, Select, DropdownMenu and Tooltip built inline `<script>` with `format!` - about 1,700 lines of measuring, flipping, outside-click and Escape handling, plus `document.currentScript` and a `window.ScrollLock` global. All of it is gone: they are layers on the overlay stack P1 M4 built, which already owns anchoring, the Escape order, the focus trap and the return of focus.
- **There were no roles.** No `role="dialog"`, no `aria-modal`, no `menu`/`menuitem`, no `tablist`, no `combobox`/`listbox`, no focus trap, and a tooltip that opened on hover only - invisible to a keyboard. Those are added, and V4 below is what holds them.
- **`slider.css` selected `input[type="range"]` bare**, which restyles the host page's own range controls. Every selector is now under `[data-rustify-scope]` and named by `data-name`, which is what V1's host-control comparison checks.

Gone with the imports: the `icons` crate (it forces `leptos/nightly`), `strum` and `validator`. `icon.rs` is ours - a container plus six glyphs, drawn on a twenty-four unit grid that the GPU glyphs share.

## The GPU half

| Category | What a region draws |
| --- | --- |
| button, checkbox, radio, switch, slider, progress, loading, icon | Drawn in full, from the same token table as the DOM half |
| scroll area | Makepad's own `ScrollBars` on a `View`; the boundary a wheel is handed back at is M6 |
| select, tabs | Experimental: the closed control and the strip are drawn and report what was asked for; the list and the panel are the DOM's |
| text field, text area | The value is drawn; editing is a native control over the rectangle (P1 M5) |
| link, tooltip, menu, dialog | Not drawn inside a region. Three are DOM layers *anchored to* one - the catalogue's own page opens a real menu against a rectangle inside the canvas - and a link is a click a region reports and the application navigates on, because a region never touches history (C-5) |

`RustifyButton` is new for a reason worth recording: makepad's own button carries makepad's theme, which in a light scope is pale text on a near-white face. A catalogue that claims both halves draw from one token table has to mean it.

## What the browser found

Four defects, all real, all found by running rather than by reading:

1. **The SDK's GPU widgets were never registered with the catalogue region's script module.** `RustifyCheckBox{}` in the script resolved to nothing and the slot drew empty - indistinguishable from a layout bug.
2. **`field +: mod.widgets.X{...}` is not how a field is given a different draw type.** `+:` extends the value a field already has; five widget definitions used it to *replace* one, failed silently at script load, and left five script types undefined.
3. **A remembered rectangle was not cleared when the page changed**, so a control that happened to land where the previous one did was never reported.
4. **A region header that does not fit is a control a pointer cannot reach.** A label, four swatches and a button across 320 pixels put the button past the edge.

## The one P1 test that fails, and what it says

`m8-endurance` "2 minutes at ten actions a second" fails on its memory
assertion. Everything it measures about *behaviour* passes: 1,200 sent, 1,200
accepted, 0 refused at 9.92/s, one live region, one live listener, no errors.
What fails is the shape of the memory curve.

```
curve 37027840,37027840,37027840,37027840,37683200,38666240,38993920,39649280,41811968,41811968,42598400,42598400
tail growth 786432 bytes; the assertion allows 418119 (1% of the tail's first sample)
```

P1 recorded `36896768 … 41680896` for the same run: "flat, a climb of 4.8 MB,
then flat again for the last third". This build starts 0.13 MB higher and ends
0.92 MB higher, and the last quarter is still climbing rather than flat.

It reproduces byte-for-byte across runs, so it is not flake. The test's own
comment says what it cannot answer: "How long a run has to be before a plateau
can be told from a slow climb is a question a two-minute run cannot answer."

**It is not M2's.** The same test was run against the build at `550c2ef`, the
commit before M2, in a worktree: it fails the same assertion, by a slightly
*larger* margin.

| Build | Total growth | Tail growth | Allowed |
| --- | --- | --- | --- |
| `550c2ef`, before M2 | 5,963,776 B | 851,968 B | 420,085 B |
| `8cd2c15`, after M2 | 5,570,560 B | 786,432 B | 418,119 B |

So M2 did not introduce it, and on this machine the two-minute run grows a
little less after M2 than before it. What the discrepancy with P1's recorded
curve shows is that the two-minute variant's flat-tail assertion is not stable
across machines: the plateau it wants to see arrives after the window closes
here, which is the limit the test's own comment names. P1's fifteen-minute
re-run after the leak fix ends at 43.5 MB and flat, and the two-hour
acceptance run is P1's to finish (its recovery snapshot lists it as an open
item).

Recorded rather than fixed here: changing the assertion or the window would be
editing P1's acceptance criterion from inside P2, and the measurement that
would justify it - a longer run - is the one P1 already has queued.

## Cost of a browser check, before and after

The plan asked for one page per `describe` instead of one per test, and it is worth recording what that bought. A cold catalogue page downloads and compiles an eleven megabyte module and boots its region: about seven seconds. With `sharedPage` (`tests/browser/support.ts`), the checks in a block cost what the work in them costs:

| Block | Tests | Wall clock |
| --- | --- | --- |
| M1 (a page per test) | 9 | ~62 s |
| M2 V2 (one shared page) | 6 | ~3 s after the first boot |
| M2 V3 (one shared page) | 5 | ~1.4 s after the first boot |
| M2 V4 (one shared page) | 9 | ~9 s after the first boot |

The price is that a shared block runs serially and each test has to put back what it touched, or read a delta rather than an absolute. That is the right trade for reads and small reversible interactions, and the wrong one for a test that changes something it cannot undo.
