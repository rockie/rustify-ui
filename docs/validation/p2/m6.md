## A-6, answered

The question was whether `--cfg=web_sys_unstable_apis` can reach the wasm build through cargo-makepad, since web-sys 0.3.105 puts `Clipboard::read_text` / `write_text` and `Navigator::clipboard` behind it (`gen_Clipboard.rs:27,48,62`, `gen_Navigator.rs:140,152`).

It can. cargo-makepad composes inherited `RUSTFLAGS` with its own (`makepad/tools/cargo_makepad/src/wasm/compile.rs:230`), so `xtask` sets the flag once in `run_cargo_makepad` and every `cargo xtask build-web` produces a clipboard-capable deployment. Setting it in `.cargo/config.toml` would **not** have worked: cargo-makepad sets the `RUSTFLAGS` environment variable, and the environment wins over the config file.

Both halves are checked, because a capability that only compiles one way is a capability that breaks somebody's build:

| Build | `cargo check --target wasm32-unknown-unknown` | `clipboard::available()` |
| --- | --- | --- |
| With the flag | passes | true |
| Without it | passes | false, and both entry points answer `Unavailable` |

A-6 is closed in the plan's assumption table and in the risk table.

## The fork change (D14)

`makepad/platform/src/os/web/web.js` cancelled every wheel event on an embedded region's canvas before delivering it (F27). A wheel that arrived after the region had run out of scroll therefore went nowhere: the page under it never moved, and no amount of work on the Rust side could fix it, because by the time the region has been pumped the browser has already been told the event was cancelled.

So the decision has to be synchronous, and the only thing that can be synchronous is a report from an earlier draw:

- `FromWasmScrollBoundary` (new): four booleans saying where the region's scrolling has run out, and the policy the region declares.
- `Cx::report_scroll_boundary(ScrollBoundary)`: called by a scrolling widget after it draws, which is the only moment the answer is a fact rather than a guess.
- `wheel_belongs_to_parent(e)` in `web.js`: consulted before `preventDefault`. The wheel goes to the page only when the region asked for that and **every axis the wheel actually moves** has run out. A region that can still scroll along one axis keeps the whole event, because splitting one wheel between two scrollers is how a diagonal gesture tears in half.

The wheel that *reaches* an edge is still the region's, because the report it is judged against is the one from before that wheel arrived. Only the wheel after it belongs to the page — which is what a person expects: the region stops, then the page moves.

**One deviation from the plan's wording.** §10 put the boundary cache in `crates/rustify-makepad/web/embedded.js`. It went into the `WasmWebBrowser` constructor in `web.js` instead, because that is the class the wheel handler lives on and `EmbeddedRegion` extends it; a cache in the subclass would have been a second place for the same fact. No change to `embedded.js` was needed.

`cd makepad && cargo test` passes with the new message, and the bridge is regenerated from the wasm on every build, so the JS and the wasm cannot disagree about it.

## What the work turned up

**A question number is not an identity.** Every drag counts its own questions from one, so a region that remembered "the last question I answered was number 1" would refuse to answer the next drag's first question. Two drags that each ask once would both be question one. The region keys on session and number together, and `every_drag_counts_its_own_questions_from_one` holds the line.

**Moving inside a region and moving into one are different.** Moving between DOM targets withdraws the previous target's yes immediately, because the thing under the pointer is what a drop lands on. Inside a region, doing the same would blank the highlight between every pointer move and its answer — a flicker, not a fact — so the answer stands until a newer one contradicts it. Arriving from *outside*, though, is a move between places, and the previous place's yes is withdrawn like any other. Two tests say so, in opposite directions.

Delivery is safe either way, because a release with a question outstanding waits for that question, so the drop is always decided by the freshest answer.

**A character is not a UTF-16 unit.** The clipboard test asked for ten thousand characters of Chinese and emoji and got 7,778: an emoji is one character and two of the units JavaScript calls `length`, so slicing by `length` both cut a surrogate pair in half and produced the wrong count. The sample is built from code points now. The application was right; the test was measuring the wrong thing, which is the failure mode a test of internationalised text is most likely to have.

**Downloads are not what `default-src 'none'` governs.** The strict policy controls what a page may load, not what it may hand the user to save, and the export needed no new directive. It is checked rather than assumed: the test compares the bytes the browser actually saved against the bytes the application meant to write.

### Two failures that were the tests, not the product

Both are worth recording because both looked like lost drops.

**A drag measured from a scrolled page.** `places()` returned viewport
coordinates, and the test before it had clicked into the property form, which
scrolled the workbench down by about 520 pixels. The next drag aimed at a canvas
that had moved: the region was never asked, so nothing was dropped, and the
count was exactly right about that. `places()` scrolls to the top and measures
from there now.

**A five-second wait for two trips through a pump.** A drop that crosses the
boundary is a question out and an answer back. Playwright's default poll is five
seconds, which is generous until the page has a two-minute endurance run behind
it. The count is still exact; what was relaxed is how long the answer may take.
