# P2 M10 report: the two failures that were older than P2

Date: 2026-09-11. Machine: macOS (Darwin 25.6.0), Apple Silicon, rustc 1.97.0-nightly (2026-05-19), Node 26.1.0, Playwright 1.63.0 (bundled Chromium, SwiftShader WebGL).

## Status

Both closed. Neither turned out to be what the ledger called it.

## `math_aot::batch_edges` was not one test, and not a test's fault

The suite reported one overflowing test. Running the file serially showed why it looked that way: a stack overflow aborts the whole binary, so whichever test reaches it first is the one that gets named. `batch_matches_single_calls` overflows on its own too - it pushes 10,001 points through the same loop.

What overflows is not the test. `makepad-stitch` is a threaded-code interpreter: every instruction ends in a sibling call to the next one, and the sibling call is a jump only after LLVM has optimised it. At `opt-level = 0` each *executed* instruction keeps its native frame until the whole function returns, so a wasm loop of a few thousand trips runs out of stack. The batch entry loops once per point inside wasm, 5,461 points to a chunk; `batch_edges` asks for 4,096 and 4,097.

Stitch says so itself - `libs/stitch/README.md` explains the dependency on sibling calls, and `libs/stitch/Cargo.toml` carries `[profile.dev] opt-level = 1`. That profile applies when stitch is the workspace root and is ignored for a path dependency, which is what it is here. So the consuming manifest asks for it:

```toml
[profile.dev.package.makepad-stitch]
opt-level = 1
```

Checked rather than assumed: `RUST_MIN_STACK=16777216` did **not** help (the depth is proportional to instructions executed, so no stack size is enough), and `cargo test --release` passed all nineteen before the change - which is what named the cause.

The root workspace needs nothing: `makepad-widgets` is a `cfg(target_arch = "wasm32")` dependency of `rustify-makepad`, so stitch is never built for the host there. The note at the top of `tests/math_aot.rs` says what a future overflow means, because the failure names the wrong test.

| Check | Before | After |
| --- | --- | --- |
| `cargo test --manifest-path platform/script/Cargo.toml` | aborts: `batch_edges` overflowed its stack | 19/19 in `math_aot`, every other file green |
| `cargo test --manifest-path platform/script/Cargo.toml --test math_aot batch_matches_single_calls` | aborts as well | passes |

## `m8-endurance`'s memory tail was a cache filling

The assertion was that the last quarter of a two-minute run is flat. It was not, and an hour of measurement says the assertion was wrong rather than the runtime.

**What was measured.** A counting global allocator in the example, reporting live bytes and live blocks by size class, plus the same probe on `fusion-basic`:

| Action, 300 rounds | Live bytes retained | Blocks |
| --- | --- | --- |
| `fusion-basic`: pointer moves and clicks over a region | 0 | 0 |
| workbench: pointer moves over the region | 88,881 | 996 |
| workbench: selection changes from the DOM | 1,331,242 | 5,406 |
| workbench: typing into the property form | 308,642 | 2,325 |
| workbench: a DOM-only toggle, a view-tab switch, idle frames | 0 | 0 |

So it was not the SDK's region path (`fusion-basic` retains nothing) and not the DOM: it was the actions that make the region draw **text it has not drawn before**.

**Two growers, both bounded, neither a leak.**

1. *The text caches.* The shaper and the layouter each hold 4,096 entries (`makepad/draw/src/text/layouter.rs`). A thousand objects have a thousand names, a thousand positions and a thousand sizes, so walking them is three thousand first sights. A two-minute run at ten actions a second is **shorter than one lap of the fixture**, so its tail was a cache still filling.
2. *Script-evaluation garbage.* Every props application that sets a shader value evaluates a small script and leaves objects behind; P1 already found this and collects at a slack of 20,000 objects (`SCRIPT_HEAP_SLACK`). Setting the slack to zero and rebuilding made the pointer-move retention disappear entirely and halved the rest - which is how the two were told apart.

**The proof that neither leaks.** A lap of 1,050 objects, then the same objects twice more:

| Pass | Live bytes retained | Per action |
| --- | --- | --- |
| First lap, 1,050 objects | 3,172,712 | ~3,021 B |
| Second pass, 300 of the same | 91,203 | 304 B |
| Third pass, 300 of the same | 93,200 | 304 B |

The second and third passes retain exactly four blocks per action - one script evaluation's garbage, reclaimed at the slack - and nothing else. Linear memory did not move at all during either.

**What changed in the test.** It walks the lap first, unpaced, and asserts the walk was complete (1,050 accepted, 0 refused); then it runs its paced window and asserts the tail is flat, which is now an assertion about a steady state rather than about a warm-up. It also asserts the comparison directly: the run must cost a fraction of the lap. The old assertion could not have caught a leak that started after the caches filled; this one can.

| Measurement | Result |
| --- | --- |
| `--project=property-workbench` | all green, `m8-endurance` included - the project has no known failure left |
| `cargo xtask verify --suite p2` | **0 automated steps failed** (the two this milestone closed were the last two) |
| Warm-up lap, 1,050 objects | accepted 1,050, refused 0, memory 39,649,280 → 44,892,160 (+5,242,880) |
| Paced run, 2 minutes at 9.92/s | sent 1,200, accepted 1,200, refused 0, errors 0, memory 44,892,160 → 45,547,520 (+655,360) |
| Tail (last quarter) | +327,680 against a threshold of 452,198 |
| Lap against run | 5,242,880 bytes for the first sight of a thousand objects, 655,360 for a longer run over the same ones |

## What this cost, and what it is worth writing down

The hunt needed four rebuilds and six browser runs. What made it converge was measuring **live** allocations rather than linear memory: wasm memory never shrinks, so a growth curve cannot tell a cache from a leak, and the size-class histogram is what separated "one script evaluation's four blocks" from "a thousand cache entries".

Both lessons are in the plan's §12.
