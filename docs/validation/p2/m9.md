## Writing the gate is what found the measurements were wrong

Three of the four numbers this report replaces were artefacts. None of them was
the build.

**A cold start was reported as 9,916 ms. It is about 160 ms.** The old figure was
timed from the Playwright process. Timing it inside the page - `performance.now()`
against the navigation's own `timeOrigin`, marked by an init script that runs
before any page script - gives 30 loads between 149 and 171 ms, of which the
module's bytes account for 26 to 34.

**Turning the HTTP cache off does not make a start cold.** Thirty loads in one
context, cache disabled, produced a bimodal curve: p50 105 ms, p95 10,033 ms.
The fast ones were Chrome's *code* cache, which the HTTP setting does not touch.
A fresh browser context per load removed the ambiguity and the bimodality with
it.

**A reload in place measures the previous page's death.** Three to six loads in
thirty came back at 10.5 s. Their own resource timings say why: the document
arrived in 1 ms and nothing was parsed until 10,460 ms. It is not the
application - `dispose()` measured 7 to 17 ms in the page - and it is not the
module, because the stall happens before the module is even requested. A
navigation in this harness costs about 10.9 s of wall clock whatever the page
does; when the new document's clock starts first, those seconds land in its
timeline. The gate gives each load a page of its own, closed before the next one
opens.

**There was no such thing as a hot start to measure.** `cargo xtask serve` sent
`Cache-Control: no-cache` and no validator, so every reload re-downloaded
everything. It now sends an `ETag` built from size and modification time - not a
hash, because hashing 11.5 MB per request trades the download for a read - and
answers `If-None-Match` with a 304. `cargo test -p xtask` covers the matching
(including a stale tag, a list, and `*`), and `curl` confirms the 304 end to end.
A fault-damaged file is still served without a validator, so the fault tests
cannot be answered from a cache.

Even so, the module is re-fetched on every hot load: a Playwright context will
not hold an 11.5 MB cache entry. The gate records that rather than pretending
otherwise; on a loopback it costs about 26 ms, and on a real link it would not.

## What the gate deliberately does not cover

Written into `budgets.ts` so that nobody quotes a pass it did not earn:

- **One machine, one browser.** R29 asks for each performance machine and fully
  supported browser to pass on its own. This is macOS Chrome under SwiftShader.
- **B0, B2 and B3.** P2 builds B1. R29's B0 column and R30's AC2/AC3 are loads
  this phase does not build, and they are recorded as not measured.
- **A throttled link.** The cold-start gate runs on the loopback, so it measures
  the machine and not the link. The throttled figures stay in `m8-network.spec.ts`
  as observations, uncompressed and therefore not a reading of AC2.

## One number that is not stable

A latency run on a busy machine came back at p95 108 ms and p99 426 ms where the
quiet runs give 42 ms and 44 ms. The budget has room for the quiet case and not
for a machine doing something else at the same time. That is in the performance
report, because a single red run should send a reader to look at the machine
before they look at the build.
