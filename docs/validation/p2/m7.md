Date: 2026-09-10. Machine: macOS (Darwin 25.6.0), Apple Silicon, rustc 1.97.0-nightly (2026-05-19), Node 26.1.0, Playwright 1.63.0 (bundled Chromium, SwiftShader WebGL), Tailwind CSS 4.1.13.

## Status

Delivered, except the part that is a person's: the twenty samples have to be compared against a reference rendering by a reviewer (A-4), and that record is not in yet. Everything a machine can check about them is checked.

## What the division of labour is

The SDK ships the words it puts on screen **on its own account** - a retry, a close, an empty answer, a refused clipboard - and nothing else. `Message` is an enum rather than free strings, so adding one means adding it to both languages: the compiler asks for the arm, and two tests check that no arm was left holding the other language's words or repeating another message.

An application's vocabulary stays the application's. The catalogue's own eighteen headings are still the catalogue's; what changed is that the *language* is one value in context, so a page cannot end up with English headings around a dialogue whose close button says 关闭.

Formatting goes through `Intl` and the options object is the application's. Whether a number is a currency and whether a date needs its year are properties of what the value means, and the SDK does not guess at them.

## What the work turned up

**A character is not a UTF-16 unit.** The clipboard test asked for ten thousand characters of Chinese and emoji and got 7,778: an emoji is one character and two of the units JavaScript calls `length`. Slicing by `length` both cut a surrogate pair in half and produced the wrong count. The sample is built from code points now. The application was right and the test was measuring the wrong thing - which is the failure a test of internationalised text is most likely to have, and worth writing down because it will happen again.

**The catalogue's local language was a second answer waiting to happen.** It had its own two-value enum, written in M2 with a comment saying M7 would replace it. It has: the page reads `rustify_ui::Locale` from context now, and the SDK's own components read the same one.

**A component's children still have to be `Send`.** The samples page holds a region, so it could not be wrapped in the catalogue's `Panel` component - the same finding as M5's splitter, and the same answer: the page holds the region itself and borrows only the classes. It is the second time this has come up, so it is in `docs/workspace.md` as well as here.

**The shipped fonts have no Arabic or Hebrew.** The theme's wide family covers Latin, Chinese and emoji. The B5 page draws right-to-left samples anyway, because the point of the page is to show what the two halves actually do; the region draws those samples with whatever that font has for absent glyphs, and the reviewer's comparison against the browser column is what records it. This is a gap in the fonts, not in the layout, and it is written into `docs/compatibility.md` rather than hidden by dropping the samples.

**Two colours in the token table failed their contrast target, and one of them mattered a lot.** White on the light theme's primary blue was 3.24:1 - under AA for anything that is not large text, and a primary button's label is not large text. The border token was 1.41:1 against the background in the light theme and 1.80:1 in the dark one, and that token is a *control's* boundary as well as a panel's edge. Both are fixed, and the ratios are a host test now (`cargo test -p rustify-ui theme`) rather than something a person squints at: a token table is exactly the kind of thing that goes wrong one value at a time, and each time it does, somebody who cannot read the result finds out first.

### One failure that was mine, and how the page now says so

The samples page would not show the missing-glyph mark. The switch moved, the
region kept drawing the samples, and nothing said which end had failed.

The cause was an edit of my own that silently matched nothing: `cargo fmt` had
reflowed the projection onto three lines after the text I was replacing was
written, so `|| blocked.get()` was never added and the page projected `None`
however the switch was set. The page compiled, the switch worked, and the region
was right.

What it changed: the page now shows what it asked for, what it projected, and
what the region drew, as three lines rather than one. When it went wrong it was
the middle one that had stopped, and neither of the other two could have said
so.

## Not done here

- The reviewer's comparison of the twenty samples against a reference rendering (A-4). The suite reports `docs/validation/p2/manual/samples.md` as missing.
- Plural rules, message interpolation, and locale-aware collation. An application that needs them should use a message library and hand the SDK only its own two languages' worth of words.
- A right-to-left *interface* language. `Direction` exists and the components are written in logical properties, so adding one would be a catalogue rather than a rewrite - but none ships, and nothing here claims one was tested.
