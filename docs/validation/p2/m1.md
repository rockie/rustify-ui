## What the first task found

M1's first task is to check the interfaces P2 assumed against the ones P1 shipped. Result: **all six exist**, four differ from the assumption, and the differences are written into the plan as §2.1. In short: `MountConfig` has one field and M4 adds to it rather than replacing it; a layer's existence is expressed by rendering it, not by an `open` prop, so the overlay components map their `open`/`on_open_change` onto that; the token names match but the component classes need eight more; and the diagnostics record has one severity, so M4 adds an informational one.

Two consequences were scheduled rather than deferred: the token table grows in the same commit as the stylesheet that reads it, and the capability catalogue moves into this crate in M2, in the same commit as the components - a catalogue moved before there is anything to catalogue is two catalogues that can disagree.

## The prefix question, answered

The plan assumed `tw_merge`'s `prefix` option would be configured to match Tailwind's. It must not be:

- Tailwind v4's `prefix(rui)` puts the prefix **before** the variants: `rui:hover:bg-primary`.
- `tw_merge`'s `prefix` option expects it **after** them: `hover:tw-bg-primary`, which is v3's shape.

Left at its default, `rui` parses as a leading variant. Because every class this crate produces carries it, two classes conflict exactly when they would have without it. Five tests hold that (`crates/rustify-components/src/macros/mod.rs`), including the case that could plausibly have broken - `rui:hover:bg-x` against `rui:bg-x` must both survive - and the case the prefix exists for: a host page's unprefixed `bg-secondary` and our `rui:bg-primary` are different classes. D13 and ADR-5 are corrected in the plan.

The other half of that risk is settled too: `prefix(rui)` **is** accepted on the split `theme.css` / `utilities.css` imports, and Tailwind's own scale variables come out prefixed (`--rui-spacing`), so they cannot collide with the SDK's tokens. Our tokens stay unprefixed because `@theme inline` passes the reference through: `.rui\:bg-primary { background-color: var(--primary) }`.

## Decisions taken here

- **The nav is buttons, not links.** The URL belongs to the router, which is M4. What the catalogue does publish is the current path, through the seam the link component reads, so M4 supplies a real URL and nothing else changes.
- **The stylesheet is committed, not generated at build time.** `build-web` therefore needs no Node. `css --check` is what makes drift a failure; it caught the catalogue's own classes missing from the product the first time it ran.
- **`build-web` copies the stylesheet for any example whose manifest names the component crate**, read from the manifest rather than from a list in the build.
- **`muted` changed meaning** from a grey text colour to the quiet surface the component classes mean by it, with `muted-foreground` for the text. One call site in property-workbench drew its hover ring in `muted` and now draws it in `muted_foreground` - the rename's one real consequence, found by looking rather than by a test, which is worth saying plainly.
